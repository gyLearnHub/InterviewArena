04 / REQUEST CHAIN

Cookie、CSRF 与跨域

登录态由两类 Cookie 协同完成；只配置其中一项，会导致登录失效或写请求被拒绝。

1LOGIN登录成功

后端签发访问令牌。

→
2COOKIES写入两类 Cookie

访问令牌使用 HttpOnly；CSRF 值允许前端读取。

→
3WRITE写请求回传 CSRF

前端在指定请求头中发送 CSRF Cookie 值。

LOGIN DIAGNOSTIC

登录状态保存不了？

从上到下检查，通常无需修改代码。

  1. 01本地 HTTP 是否设置了 AUTH_COOKIE_SECURE=false
  2. 02浏览器来源是否与 CORS_ALLOWED_ORIGINS 完全一致
  3. 03前端请求是否允许携带 Cookie
  4. 04写请求是否回传 X-CSRF-Token
  5. 05修改环境变量后是否已经重启对应进程
跨站部署

前后端真正跨站时使用 AUTH_COOKIE_SAMESITE=none，并且必须同时启用 AUTH_COOKIE_SECURE=true。

05 / DATA SAFETY

数据库初始化与升级

迁移带版本记录和 MySQL 命名锁。重复执行会跳过已完成版本，多实例不会同时改表。

NEW DATABASE

新环境

创建基础表，并执行全部版本化迁移。

python backend\scripts\init_db.py
EXISTING DATABASE

已有数据库

只执行尚未应用的版本化迁移。

python backend\scripts\migrate_v1.py

PRODUCTION MIGRATION

01备份数据库先确认备份可恢复
02执行迁移在发布阶段单独运行
03启动实例关闭启动时自动迁移
04检查就绪确认关键检查无失败

06 / SYSTEM PULSE

健康检查

存活检查回答“进程是否响应”，就绪检查回答“服务是否具备接收真实请求的条件”。

LIVENESS

/api/health

API 进程可响应时返回 HTTP 200。

{"status":"ok"}
READINESS

/api/health/ready

检查配置、MySQL、目录和后台任务运行器。

ok · 200degraded · 200failed · 503
PowerShell 
Invoke-RestMethod http://127.0.0.1:8000/api/health
Invoke-RestMethod http://127.0.0.1:8000/api/health/ready

07 / QUALITY GATE

质量保障

根据改动范围选择检查级别。核心流程或发布前验证应包含 E2E。

FAST

快速检查

日常开发和小范围修改。

scripts\quality.ps1
FULL

全量检查

合并前或同时涉及前后端。

scripts\quality.ps1 -Full
FLOW

包含 E2E

核心用户流程或发布前验证。

scripts\quality.ps1 -E2E
首次运行 E2E

先在 frontend 目录执行 npx playwright install chromium --only-shell。
